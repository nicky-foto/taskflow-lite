## Agent Brief

**Category:** bug
**Summary:** A task created after a delete can share its id with an existing task, so status changes hit the wrong task

**Current behavior:**
After any task is deleted, the next created task can receive an id that an existing task already has, possibly in another
workspace. Changing or deleting the new task acts on the older task: a Lead gets `ForbiddenError`, a Member of both
workspaces silently changes the other workspace's task.

**Desired behavior:**
Every task id is unique for the life of the store and is never reused, even after deletes. Status changes and deletes
always act on the task the user picked.

**Key interfaces:**
- `createTask()`: the id it assigns must never collide with any existing or past task id
- `Store`: may need to carry whatever state makes ids unique

**Acceptance criteria:**
- [x] After delete + create, all task ids in the store are distinct
- [x] The reported steps: the Lead can change the new task's status; the Finance task is unchanged
- [x] Regression test fails on the old code and passes on the fix

**Out of scope:**
- Changing the id format visible in the UI
- Persisting tasks to a database

**Resolution:** fixed. Correct hypothesis (#1 of 4): ids were derived from `tasks.length`, so a delete made the next
id collide; `find()` returned the older task. Ids now come from a counter that only goes up (ADR-0003).
Regression test: `tests/task-id.regression.test.ts`.
